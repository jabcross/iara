● Relay sub-agent findings on Preesm frontend hazards, then handle cleanup.

  Why Preesm frontend-bound (3.7× idq gap)

  Sub-agent read Preesm Core0.c–Core3.c/main.c. Root: call density, not compute.

  1. Sync-call flood (top hazard). Core0.c = 47 kernel calls, but 1500 comm 
  calls — 594 sendStart + 594 sendEnd + 156 receiveStart + 156 receiveEnd. ~32:1
  comm:compute. Workers 10–13:1. Every call+ret = 2 taken-branch resteers →
  frontend bubbles even when predicted right. This IS the idq_uops_not_delivered
  gap.

  2. 750 pure-resteer calls. sendEnd() and receiveStart() are empty functions
  (communication.c). 750 do-nothing call/rets in Core0.c = resteers for zero
  work.

  3. receiveEnd → rk_sema_wait spin: do { r = sem_wait(&s->sem); } while (r == 
  -1);

  4. 485KB unrolled mega-function. One straight-line computationThread_Core0
  (lines 2117–5050), -O3 no -flto. Overflows DSB/uop-cache (~1.5K uop), strains
  32KB L1i.

  5. BB fragmentation. 42 Fork + 36 Join + 61 Broadcast empty/comment blocks;
  609 // memcpy comments, 1 real memcpy.

  Not hazards: no switch/fn-ptr dispatch in hot loop; kernel args are
  compile-time literals.

  Contrast IaRa: each kernel called once in tight loop → tiny resident schedule
  stays in DSB; runtime handles sync vs Preesm's ~30 out-of-line comm calls per
  kernel. Explains IPC 2.35 vs 1.77 on identical kernel machine code.
