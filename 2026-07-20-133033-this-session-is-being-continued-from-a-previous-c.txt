● Good question — "frontend/backend" is CPU-pipeline terminology, and it's the
  key to reading our result. Step by step.

  1. The CPU is a two-stage assembly line

  A modern core (this Xeon 6252) doesn't execute one instruction at a time. It's
  a pipeline split into two halves:

     ┌─────────────── FRONTEND ───────────────┐   ┌──────────────── BACKEND
  ────────────────┐
     fetch bytes → decode → emit µops  ──IDQ──►  rename → schedule → execute →
  retire
     "what to do next"                  queue    "actually do it"

  - Frontend = the supply side. It figures out which instructions come next,
  reads their bytes from the instruction cache, decodes them into µops
  (micro-ops — the CPU's internal RISC-like operations), and drops those µops
  into a queue (the IDQ, Instruction Decode Queue).
  - Backend = the consumer side. It pulls µops from the IDQ, finds their input
  data, runs them on execution units (add, multiply, load, store), and retires
  them (commits results in program order).

  The two run concurrently. The frontend races ahead fetching/decoding while the
  backend chews through what's already queued.

  2. The core can start 4 µops per cycle — "issue slots"

  Every clock cycle, the backend has 4 issue slots — 4 openings to accept a µop
  from the IDQ. slots = 4 × cycles. That's the theoretical max throughput. The
  top-down method asks, for every single slot, one question: what happened to 
  it?

  Each slot falls into exactly one of four buckets:

                          ┌─ was a µop delivered AND did it retire? → RETIRING
     (useful work)
     this issue slot ─────┤   delivered but squashed (wrong branch)? → BAD
  SPECULATION
                          │   frontend had NO µop ready to give?      →
  FRONTEND-BOUND
                          └─ frontend HAD one but backend refused it? →
  BACKEND-BOUND

  - Retiring = the slot did real work. Want this near 100%.
  - Bad speculation = the core guessed a branch wrong, ran ahead, threw the work
  away. Wasted.
  - Frontend-bound = the slot was empty because the frontend couldn't deliver a 
  µop in time — starved for instructions.
  - Backend-bound = the frontend had a µop ready, but the backend couldn't take
  it — stalled waiting on data (cache/memory), or all execution ports busy.

  This is the crucial split: backend-bound means "waiting on data/compute"
  (that's where cache misses, memory bandwidth, port pressure show up).
  frontend-bound means "waiting to even know what to run" — a completely
  different problem, upstream of memory.

  3. The one counter that measures it: idq_uops_not_delivered

  That counter literally counts issue slots where the frontend handed the 
  backend nothing while the backend was ready to accept. It is the
  frontend-bound bucket, in raw slot units.

  Our data:

  ┌────────────────────────┬────────┬────────┐
  │                        │ preesm │ enkits │
  ├────────────────────────┼────────┼────────┤
  │ cycles                 │ 34.2B  │ 25.4B  │
  ├────────────────────────┼────────┼────────┤
  │ slots (4×cycles)       │ 137B   │ 102B   │
  ├────────────────────────┼────────┼────────┤
  │ idq_uops_not_delivered │ 10.8B  │ 2.9B   │
  ├────────────────────────┼────────┼────────┤
  │ → frontend-bound %     │ ~7.9%  │ ~2.8%  │
  └────────────────────────┴────────┴────────┘

  preesm wastes 10.8B slots to an empty frontend — 3.7× more than enkits. Those
  are cycles where preesm's backend sat idle not because it was waiting on 
  memory, but because the frontend hadn't figured out / fetched / decoded the
  next instructions yet.

  4. Why this rules out the whole memory story

  Memory problems — cache misses, bandwidth, TLB, contention — are backend-bound
  symptoms. The frontend already delivered the load µop; the backend is stuck
  waiting for the data to come back. If preesm's problem were memory, its wasted
  slots would be backend-bound, and we'd see it in the by-level stall counters.

  But we measured those directly and they were identical to enkits
  (L1d/L2/L3-miss stalls equal; bandwidth 3–6% of peak). So preesm's extra
  cycles are not in the backend waiting on data — they're in the frontend, not
  delivering instructions. That's why every memory hypothesis died: we were
  looking in the wrong half of the pipeline.

  5. What starves preesm's frontend specifically

  The frontend can run dry for a few reasons:

  1. I-cache misses — the instruction bytes aren't cached. → we measured
  icache_64b.iftag_stall: preesm 19M vs enkits 42M. Worse in enkits. Not it.
  2. DSB↔MITE switches — the frontend has a fast path (DSB, a cache of
  already-decoded µops) and a slow legacy decode path (MITE); bouncing between
  them costs cycles. → preesm 600M vs enkits 1010M. Worse in enkits. Not it.
  3. Branch resteers — this is the remaining suspect. Every time the code takes
  a branch (a jump, a function call/return), the frontend was fetching straight 
  ahead and now has to throw that away and re-steer to the branch target. Even a
  correctly predicted taken branch costs a bubble; a call/return does too. Code
  that is lots of short calls and jumps — not tight compute loops — keeps
  re-steering the frontend and starving the IDQ.

  That last one fits the structure exactly. The compute kernels are identical in

  - IaRa/enkits: the runtime calls a kernel, the kernel runs a long tight inner

  - Preesm: its generated Core0.c orchestration code is a long straight-line
  sequence of many actor-firing calls, index math, and buffer-offset setup
  between kernel invocations. More branches/calls per unit of real work → more

  orchestration code is more branch-dense, and that branchiness starves the 
  pipeline's instruction supply. IaRa's runtime spends its cycles inside tight
  kernel loops.
